Sindhi Tokenizer Documentation

Release: v1.0.0 Script: Perso-Arabic (sd) Algorithm: SentencePiece Unigram Flagship Vocab: 64,000 0.0000% Character Loss

The Sindhi Tokenizer Project provides production-grade, lossless subword tokenizers for the Sindhi language in its standard 52-letter Perso-Arabic script. By training a Byte-Fallback SentencePiece Unigram model on a balanced 1.49M sentence corpus, this project resolves severe character fragmentation and silent deletion defects observed in current general-purpose multilingual LLMs and existing monolingual models.

The flagship CustomSindhi_64k model achieves an average subword fertility of 1.147 tokens per word and 88.6% single-token word coverage across four evaluation registers, improving tokenization efficiency by 24.1% over XLM-RoBERTa and 60.4% over LLaMA 3.2.

Overview & Key Findings

Sindhi (سنڌي) is an Indo-Aryan language spoken by over 35 million people, written in an extended Perso-Arabic alphabet with 52 characters. It features distinctive linguistic properties that pose severe challenges to off-the-shelf NLP tokenizers:

  • Phonemic Richness: Four implosive consonants (ٻ, ڄ, ڏ, ڳ), distinctive retroflexes, and aspirated digraphs (ڀ, ٿ, ڇ, ڍ, ڦ, ڳ, ڱ).
  • Complex Morphology: Extensive pronominal clitic suffixation where prepositions and pronouns attach directly to verbs and nouns (e.g., ڪتابم "my book", ڏنم "I gave").
  • Etymological Diversity: Heavy borrowing from Sanskrit, Arabic, and Persian, requiring subword vocabularies to share roots without fragmenting loan stems.

When evaluated on standard Sindhi corpora, standard frontier models suffer from subword bloat: LLaMA 3.2 fragments Sindhi at 2.896 tokens per word, with 28.5% of characters degenerating into byte-level fallbacks. Meanwhile, existing community Sindhi tokenizers suffer from silent character deletion (e.g., TinyLlama dropping ہ in 24.9% of sentences).

Core Contribution
We release four custom SentencePiece Unigram tokenizers trained with 100% character coverage and byte fallback enabled, completely eliminating UNK tokens and character loss while achieving state-of-the-art fertility.

Installation & Quick Start

The tokenizers can be used either through the official Google SentencePiece Python library or via Hugging Face's transformers library.

1. Installation

bash 
# Install required runtime dependencies
pip install sentencepiece transformers tokenizers

2. Native SentencePiece Usage (Recommended)

Loading via SentencePiece directly is the most robust and performant interface:

python 
import sentencepiece as spm

# Initialize processor with trained model file
sp = spm.SentencePieceProcessor()
sp.load("tokenizers/custom_unigram_64k/sindhi_unigram_64000.model")

text = "سنڌ جي تاريخ تمام قديم ۽ وسيع ثقافتي ورثي تي مشتمل آهي"

# Encode to subword tokens and IDs
pieces = sp.encode_as_pieces(text)
ids = sp.encode_as_ids(text)

print("Subword Pieces:", pieces)
# [' سنڌ', ' جي', ' تاريخ', ' تمام', ' قديم', ' ۽', ' وسيع', ' ثقافتي', ' ورثي', ' تي', ' مشتمل', ' آهي']
print("Token IDs:", ids)

# Lossless decode
decoded = sp.decode_pieces(pieces)
assert decoded == text, "Lossless reconstruction guaranteed"

3. Hugging Face Transformers Integration

You can load the published tokenizer directly from the Hugging Face Hub using PreTrainedTokenizerFast:

python 
from transformers import PreTrainedTokenizerFast

# Load from Hugging Face Model Hub
tokenizer = PreTrainedTokenizerFast.from_pretrained("alinawazmahar/sindhi-tokenizer")

text = "خداوند ڪريم کيس اعليٰ ذهانت سان نوازيو هو"
inputs = tokenizer(text, return_tensors="pt")
tokens = tokenizer.convert_ids_to_tokens(inputs["input_ids"][0])
print(tokens)
Critical Compatibility Note: Do Not Use LlamaTokenizer Directly
Do not initialize transformers.LlamaTokenizer directly on the raw .model file. LlamaTokenizer assumes a hard-coded 32k BPE structure and silently corrupts custom Unigram vocabularies (often reducing them to 3 tokens). Always load via PreTrainedTokenizerFast or use the provided SPMTokenizerAdapter class in evaluation/metrics.py.

Linguistic Motivation

Tokenization is the foundational layer of any Large Language Model. When a tokenizer is sub-optimally trained for a script, downstream models suffer from two primary penalties:

1. Context Window Degradation
If a language requires 2.90 tokens per word (like Sindhi under LLaMA 3.2) compared to 1.15 in our custom tokenizer, an 8,192-token context window can only fit 2,820 Sindhi words instead of 7,120 words. This 60% loss in effective context window length severely restricts document summarization, retrieval-augmented generation (RAG), and few-shot reasoning.
2. Quadractic Attention Cost
Transformer self-attention scales quadratically with sequence length ($O(N^2)$). A 2.5× increase in token count per word leads to a ~6.25× increase in attention computation during pretraining and inference.
3. Character Deletion and Semantic Drift
Tokenizers with incomplete character coverage or faulty normalization silently drop characters. In Sindhi, stripping the single letter ہ (HEH GOAL, U+06C1) alters word meanings entirely: هي (this) becomes ي, and ڪريو is corrupted.

SentencePiece Methodology

Unlike Byte-Pair Encoding (BPE), which iteratively merges frequent character pairs deterministically from the bottom up, the Unigram language model (Kudo, 2018) starts with an oversized vocabulary of candidate substrings and iteratively prunes candidates based on their marginal contribution to the corpus log-likelihood.

During tokenization, the Unigram model segments input strings by maximizing the joint probability under the Viterbi algorithm:

mathematical formulation
x* = argmax_{x in S(X)} prod_{i=1}^{M} P(x_i)

Where $S(X)$ is the set of all valid segmentations of input $X$, and $P(x_i)$ is the probability of subword token $x_i$. This probabilistic approach provides two key advantages for Sindhi:

  1. Linguistically Sound Morphological Boundaries: Inflections, case markers, and clitic suffixes are detached cleanly rather than creating unnatural cross-morpheme concatenations.
  2. Subword Regularization: SentencePiece Unigram natively supports sampling alternative segmentations during pretraining, improving downstream neural network robustness to typos and dialectal spelling variants.

Training Configuration

Hyperparameter Value Rationale
model_type unigram Probabilistic pruning yields superior morpheme preservation over greedy BPE.
character_coverage 1.0 Ensures all 52 Sindhi characters, numerals, and punctuation are represented.
byte_fallback True Decomposes unseen rare Unicode points into UTF-8 bytes; eliminates <unk> tokens.
normalization_rule_name nfkc Unifies presentation forms while preserving distinctive Sindhi diacritics and letters.
split_by_whitespace True Prevents tokens from spanning across word boundaries.
remove_extra_whitespaces False Preserves exact spacing and indentation for code and formatted documents.

Corpus Architecture & Preprocessing

The training dataset comprises 1,490,000 deduplicated sentences (~28.4 million words) collected and curated specifically to prevent domain overfitting. The corpus employs a 70 / 15 / 15 register distribution:

Corpus Component Proportion Sentence Count Source Domains & Linguistic Purpose
Core Sindhi Monolingual 70.0% 1,043,000 Sindhi Wikipedia, news portals (Kawish, Awami Awaz), literary prose, governmental gazettes, textbooks. Establishes native Sindhi unigram frequencies.
Regional Perso-Arabic Anchor 15.0% 223,500 Urdu, Arabic, and Persian parallel religious and legal texts. Anchors shared vocabulary to prevent cross-lingual stem shattering.
Technical & Code-Switched 15.0% 223,500 Science, computing, mathematics, and English transliterations. Ensures robustness against mixed-script documents and programming syntax.

Text Normalization Pipeline

Perso-Arabic script in digital media frequently contains encoding ambiguities resulting from inconsistent keyboard layouts (e.g., Arabic Kaf ك vs. Sindhi Kaf ڪ, and Arabic Yeh ي vs. Farsi Yeh ی). The preprocessing pipeline enforces standard Sindhi orthography:

python — training/preprocessor.py 
import unicodedata
import re

def normalize_sindhi(text: str) -> str:
    # 1. Unicode NFKC normalization
    text = unicodedata.normalize("NFKC", text)

    # 2. Harmonize common regional character collisions
    REPLACEMENTS = {
        "\u0643": "\u06aa",  # Arabic Kaf -> Sindhi Kaf (ڪ)
        "\u06cc": "\u064a",  # Farsi Yeh -> Arabic/Sindhi Yeh (ي)
        "\u06be": "\u0647",  # Do-chashmi Heh -> Heh (where inappropriate)
        "\u200c": "",        # Remove superfluous Zero-Width Non-Joiners
        "\u200d": "",        # Remove Zero-Width Joiners
    }
    for old, new in REPLACEMENTS.items():
        text = text.replace(old, new)

    # 3. Collapse duplicate whitespace
    text = re.sub(r"[ \t]+", " ", text)
    return text.strip()

Evaluation Methodology

To avoid benchmark bias, evaluation was conducted across four distinct textual registers totaling 40,000 sentences (10,000 sentences per register):

  1. Formal Sindhi Prose: Literary publications, historical archives, and academic texts.
  2. Conversational / Social Media: Informal Facebook, Twitter/X, and forum posts exhibiting colloquial spelling variations.
  3. Technical / Educational: Science, IT, and medical documents containing domain-specific loanwords.
  4. FLORES+ Sindhi Benchmark: Standard Wikipedia translation test split from Meta's FLORES+ suite.

Evaluated Metrics

  • Subword Fertility (tokens/word) ↓: Ratio of total generated subwords to whitespace-delimited words. Ideal value approaches 1.0.
  • Single-Token Word % ↑: Percentage of words in the vocabulary represented as a complete single subword token.
  • Out-of-Vocabulary (UNK) Rate % ↓: Percentage of input words that trigger an <unk> token. Must be 0.000%.
  • Byte-Fallback Rate % ↓: Percentage of tokens emitted as raw UTF-8 byte pieces (e.g., <0xD8>).
  • Round-Trip Character Loss % ↓: Normalized Character Error Rate (CER) between original string $S$ and $S' = \text{decode}(\text{encode}(S))$. Evaluated unconditionally across all registers.

Key Takeaways from the Matrix

  1. Unconditional Superiority at ≥64k: CustomSindhi (64k, 100k, 150k) outperforms all 13 baseline tokenizers across all 4 registers simultaneously. At 32k, only TinyLlama_Sindhi records lower fertility on the FLORES+ split, but it carries a fatal character-deletion defect.
  2. Drastic Multilingual Fragmentation: LLaMA 3.2 fragments Sindhi at 2.896 tokens per word with 28.5% byte fallback, while BLOOM fragments at 2.627 with 31.7% byte fallback. Our 64k model improves efficiency by 60.4% over LLaMA 3.2.
  3. Zero Data Loss: CustomSindhi achieves an absolute 0.0000% character error rate across all tested corpora.

Defect Analysis: Character Deletion in Baselines

During evaluation, automated round-trip consistency tests ($S \to \text{encode} \to \text{decode} \to S'$) uncovered critical silent data-corruption defects in prominent open-source Sindhi tokenizers:

Defect 1: TinyLlama_Sindhi Silently Deletes U+06C1 (HEH GOAL)

TinyLlama_Sindhi (a 42,681-vocab community model) exhibits a 0.4147% worst-case character loss, corrupting 24.9% of all evaluated Sindhi sentences. Because the character ہ (U+06C1) was omitted from its training vocabulary and byte fallback was disabled, the tokenizer deletes the character without warning:

  • Input: هي ڪتاب تمام سٺو آهي
  • TinyLlama Reconstructed: ي ڪتاب تمام سٺو آي (هي corrupted to ي; آهي corrupted to آي)
Defect 2: FahadQazi_BPE Silently Deletes ASCII/Latin Characters

FahadQazi_BPE (a 13,031-vocab BPE model) exhibits a 0.8461% character loss, corrupting 16.2% of sentences. It silently discards Latin alphabet characters (A–Z, a–z), destroying URLs, brand names, code snippets, and English loanwords.

In contrast, CustomSindhi models guarantee 100% character preservation. Every valid Unicode codepoint is either matched by a dedicated subword piece or cleanly decomposed into reversible UTF-8 byte tokens.

Frequently Asked Questions

SentencePiece Unigram operates via global likelihood maximization and subword pruning rather than greedy bottom-up merges. In Sindhi, where prefixes, stems, and pronominal clitic suffixes frequently concatenate, Unigram preserves true morphological roots far more reliably than BPE. Furthermore, Unigram natively supports subword regularization during downstream model training.
Our empirical Pareto analysis indicates that expanding vocabulary from 64k to 150k only yields a marginal fertility improvement of 0.022 tokens/word (1.147 to 1.125), while increasing embedding table memory by over 134%. 64k achieves the optimal equilibrium of compact model footprint and single-token word coverage (88.6%).
When byte_fallback=True is specified in SentencePiece, any character absent from the subword vocabulary is decomposed into its individual raw UTF-8 byte tokens (values from 0x00 to 0xFF). Because every Unicode character has a well-defined UTF-8 byte representation, the model never emits an unknown token symbol and decoding remains perfectly lossless.
In many legacy Hugging Face tokenizer configurations, missing characters without a mapped UNK token are silently dropped during parsing. This created an illusion of zero unknown tokens while quietly destroying 24.9% of sentences. Our round-trip normalized edit distance test was explicitly designed to expose this silent data loss.
Yes. The trained .model and Hugging Face tokenizer.json files can be used directly as the base tokenizer or merged with existing multilingual vocabularies using vocabulary expansion techniques (e.g., via transformers.PreTrainedTokenizerFast).
