Sindhi Tokenizer Documentation

SDK release: v1.1.0 Script: Perso-Arabic (sd) Algorithm: SentencePiece Unigram Flagship Vocab: 64,000 0.0000% normalized-length loss on evaluated text

The Sindhi Tokenizer Project provides SentencePiece Unigram subword tokenizers for the Sindhi language in its standard 52-letter Perso-Arabic script. By training a Byte-Fallback SentencePiece Unigram model on a 1.46M+ sentence corpus, this project measures character fragmentation and silent deletion defects observed in current general-purpose multilingual LLMs and existing monolingual models.

The Python SDK is published on PyPI as sindhi-tokenizer. Install it with pip and use the SindhiTokenizer API to load a released model, tokenize text, encode IDs or pieces, decode text, and process batches. The SDK supports Python 3.9–3.12; model files are downloaded separately from Hugging Face and cached locally.

The flagship CustomSindhi_64k model achieves an average subword fertility of 1.147 tokens per word and 88.6% single-token word coverage across four evaluation registers, improving tokenization efficiency by 24.1% over XLM-RoBERTa and 60.4% over LLaMA 3.2.

Overview & Key Findings

Sindhi (سنڌي) is an Indo-Aryan language spoken by over 35 million people, written in an extended Perso-Arabic alphabet with 52 characters. It features distinctive linguistic properties that pose severe challenges to off-the-shelf NLP tokenizers:

  • Phonemic Richness: Four implosive consonants (ٻ, ڄ, ڏ, ڳ), distinctive retroflexes, and aspirated digraphs (ڀ, ٿ, ڇ, ڍ, ڦ, ڳ, ڱ).
  • Complex Morphology: Extensive pronominal clitic suffixation where prepositions and pronouns attach directly to verbs and nouns (e.g., ڪتابم "my book", ڏنم "I gave").
  • Etymological Diversity: Heavy borrowing from Sanskrit, Arabic, and Persian, requiring subword vocabularies to share roots without fragmenting loan stems.

When evaluated on standard Sindhi corpora, standard frontier models suffer from subword bloat: LLaMA 3.2 fragments Sindhi at 2.896 tokens per word, with 28.5% of characters degenerating into byte-level fallbacks. Meanwhile, existing community Sindhi tokenizers suffer from silent character deletion (e.g., TinyLlama dropping ہ in 24.9% of sentences).

Core Contribution
We release four custom SentencePiece Unigram tokenizers trained with 100% character coverage and byte fallback enabled. The custom models produced no UNK tokens and no normalized-length loss on the evaluated text; this length-based check does not prove exact character identity for arbitrary inputs.

Python SDK: Installation & Quick Start

The recommended way to use the released tokenizer models is the sindhi-tokenizer Python SDK on PyPI. It supports Python 3.9–3.12 and installs the two runtime dependencies it needs: SentencePiece and the Hugging Face Hub client. You do not need to clone this repository to use the SDK.

1. Install from PyPI

PowerShell, macOS, or Linux 
python -m pip install --upgrade sindhi-tokenizer

PyPI package: sindhi-tokenizer. The SDK wheel contains the Python package, not the model files. The first call to from_pretrained() downloads the selected model from Hugging Face; later calls reuse the Hugging Face Hub cache. To pin the release documented here, install sindhi-tokenizer==1.1.0.

A virtual environment is recommended to keep dependencies separate from other projects:

Windows PowerShell 
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install sindhi-tokenizer
macOS or Linux 
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install sindhi-tokenizer

2. Load the recommended model and tokenize

python 
from sindhi_tokenizer import SindhiTokenizer

# Defaults to the recommended 64,000-piece model.
tokenizer = SindhiTokenizer.from_pretrained()
text = "سنڌ جي تاريخ تمام قديم آهي"

pieces = tokenizer.tokenize(text)
token_ids = tokenizer.encode(text)

print("Pieces:", pieces)
print("Token IDs:", token_ids)
print("Vocabulary size:", tokenizer.vocab_size)  # 64000

decoded = tokenizer.decode(token_ids)
assert decoded == text
print("Decoded:", decoded)

Four vocabulary sizes are available: 32000, 64000, 100000, and 150000. Pass the size when loading a different model:

python 
from sindhi_tokenizer import SindhiTokenizer

tokenizer_100k = SindhiTokenizer.from_pretrained(vocab_size=100000)
pieces = tokenizer_100k.encode("سنڌي ٻولي", out_type="pieces")
print(pieces)

3. Batch processing and local model files

encode() returns integer IDs by default. Use out_type="pieces" for readable SentencePiece strings. The SDK also provides batch methods and can load a local SentencePiece .model file.

python 
from sindhi_tokenizer import SindhiTokenizer

tokenizer = SindhiTokenizer.from_pretrained()
texts = ["سنڌ جي تاريخ", "هي سنڌي ٽوڪنائزر آهي"]
batch_ids = tokenizer.encode_batch(texts)
decoded_texts = tokenizer.decode_batch(batch_ids)
assert decoded_texts == texts

pieces = tokenizer.encode(texts[0], out_type="pieces")
ids = tokenizer.encode(texts[0])
assert tokenizer.decode(pieces) == texts[0]
assert tokenizer.id_to_piece(ids[0]) == pieces[0]
assert tokenizer.piece_to_id(pieces[0]) == ids[0]

# Replace this example path with a local model file.
local_tokenizer = SindhiTokenizer.from_file("path/to/sindhi_custom_64000.model")

If a model has already been cached, local_files_only=True prevents an online lookup:

python 
from sindhi_tokenizer import SindhiTokenizer

tokenizer = SindhiTokenizer.from_pretrained(local_files_only=True)

4. Test an installation

Run this short check after installation. The first model load requires internet access to Hugging Face; later loads use the local Hub cache.

python 
from sindhi_tokenizer import SindhiTokenizer

tokenizer = SindhiTokenizer.from_pretrained()
text = "سنڌ جي تاريخ تمام قديم آهي"
ids = tokenizer.encode(text)
assert tokenizer.decode(ids) == text
print("SDK works; vocabulary:", tokenizer.vocab_size)

Linguistic Motivation

Tokenization is the foundational layer of any Large Language Model. When a tokenizer is sub-optimally trained for a script, downstream models suffer from two primary penalties:

1. Context Window Degradation
If a language requires 2.90 tokens per word (like Sindhi under LLaMA 3.2) compared to 1.15 in our custom tokenizer, an 8,192-token context window can only fit 2,820 Sindhi words instead of 7,120 words. This 60% loss in effective context window length severely restricts document summarization, retrieval-augmented generation (RAG), and few-shot reasoning.
2. Quadractic Attention Cost
Transformer self-attention scales quadratically with sequence length ($O(N^2)$). A 2.5× increase in token count per word leads to a ~6.25× increase in attention computation during pretraining and inference.
3. Character Deletion and Semantic Drift
Tokenizers with incomplete character coverage or faulty normalization silently drop characters. In Sindhi, stripping the single letter ہ (HEH GOAL, U+06C1) alters word meanings entirely: هي (this) becomes ي, and ڪريو is corrupted.

SentencePiece Methodology

Unlike Byte-Pair Encoding (BPE), which iteratively merges frequent character pairs deterministically from the bottom up, the Unigram language model (Kudo, 2018) starts with an oversized vocabulary of candidate substrings and iteratively prunes candidates based on their marginal contribution to the corpus log-likelihood.

During tokenization, the Unigram model segments input strings by maximizing the joint probability under the Viterbi algorithm:

mathematical formulation
x* = argmax_{x in S(X)} prod_{i=1}^{M} P(x_i)

Where $S(X)$ is the set of all valid segmentations of input $X$, and $P(x_i)$ is the probability of subword token $x_i$. This probabilistic approach provides two key advantages for Sindhi:

  1. Linguistically Sound Morphological Boundaries: Inflections, case markers, and clitic suffixes are detached cleanly rather than creating unnatural cross-morpheme concatenations.
  2. Subword Regularization: SentencePiece Unigram natively supports sampling alternative segmentations during pretraining, improving downstream neural network robustness to typos and dialectal spelling variants.

Training Configuration

Hyperparameter Value Rationale
model_type unigram Probabilistic pruning yields superior morpheme preservation over greedy BPE.
character_coverage 1.0 Ensures all 52 Sindhi characters, numerals, and punctuation are represented.
byte_fallback True Decomposes unseen rare Unicode points into UTF-8 bytes; eliminates <unk> tokens.
normalization_rule_name nfkc Unifies presentation forms while preserving distinctive Sindhi diacritics and letters.
split_by_whitespace True Prevents tokens from spanning across word boundaries.
remove_extra_whitespaces False Preserves exact spacing and indentation for code and formatted documents.

Corpus Architecture & Preprocessing

The training dataset comprises 1,490,000 deduplicated sentences (~28.4 million words) collected and curated specifically to prevent domain overfitting. The corpus employs a 70 / 15 / 15 register distribution:

Corpus Component Proportion Sentence Count Source Domains & Linguistic Purpose
Core Sindhi Monolingual 70.0% 1,043,000 Sindhi Wikipedia, news portals (Kawish, Awami Awaz), literary prose, governmental gazettes, textbooks. Establishes native Sindhi unigram frequencies.
Regional Perso-Arabic Anchor 15.0% 223,500 Urdu, Arabic, and Persian parallel religious and legal texts. Anchors shared vocabulary to prevent cross-lingual stem shattering.
Technical & Code-Switched 15.0% 223,500 Science, computing, mathematics, and English transliterations. Ensures robustness against mixed-script documents and programming syntax.

Text Normalization Pipeline

Perso-Arabic script in digital media frequently contains encoding ambiguities resulting from inconsistent keyboard layouts (e.g., Arabic Kaf ك vs. Sindhi Kaf ڪ, and Arabic Yeh ي vs. Farsi Yeh ی). The preprocessing pipeline enforces standard Sindhi orthography:

python — training/preprocessor.py 
import unicodedata
import re

def normalize_sindhi(text: str) -> str:
    # 1. Unicode NFKC normalization
    text = unicodedata.normalize("NFKC", text)

    # 2. Harmonize common regional character collisions
    REPLACEMENTS = {
        "\u0643": "\u06aa",  # Arabic Kaf -> Sindhi Kaf (ڪ)
        "\u06cc": "\u064a",  # Farsi Yeh -> Arabic/Sindhi Yeh (ي)
        "\u06be": "\u0647",  # Do-chashmi Heh -> Heh (where inappropriate)
        "\u200c": "",        # Remove superfluous Zero-Width Non-Joiners
        "\u200d": "",        # Remove Zero-Width Joiners
    }
    for old, new in REPLACEMENTS.items():
        text = text.replace(old, new)

    # 3. Collapse duplicate whitespace
    text = re.sub(r"[ \t]+", " ", text)
    return text.strip()

Evaluation Methodology

To avoid benchmark bias, evaluation was conducted across four distinct textual registers totaling 40,000 sentences (10,000 sentences per register):

  1. Formal Sindhi Prose: Literary publications, historical archives, and academic texts.
  2. Conversational / Social Media: Informal Facebook, Twitter/X, and forum posts exhibiting colloquial spelling variations.
  3. Technical / Educational: Science, IT, and medical documents containing domain-specific loanwords.
  4. FLORES+ Sindhi Benchmark: Standard Wikipedia translation test split from Meta's FLORES+ suite.

Evaluated Metrics

  • Subword Fertility (tokens/word) ↓: Ratio of total generated subwords to whitespace-delimited words. Ideal value approaches 1.0.
  • Single-Token Word % ↑: Percentage of words in the vocabulary represented as a complete single subword token.
  • Out-of-Vocabulary (UNK) Rate % ↓: Percentage of input words that trigger an <unk> token. Must be 0.000%.
  • Byte-Fallback Rate % ↓: Percentage of tokens emitted as raw UTF-8 byte pieces (e.g., <0xD8>).
  • Normalized-Length Loss % ↓: Length decrease between normalized input string $S$ and $S' = \text{decode}(\text{encode}(S))$ after NFKC canonicalization: $\frac{\text{len}(S) - \text{len}(S')}{\text{len}(S)}$. Evaluated unconditionally across all registers.

Key Takeaways from the Matrix

  1. Fertility and Retention at ≥64k: CustomSindhi (64k, 100k, 150k) has the lowest fertility and highest single-token retention of all 14 baseline tokenizers in all 4 registers. On FLORES+ the margin at 64k is 0.002 fertility (parity), and no significance tests were run. (On byte fallback, Gemma 3 achieves 0.105% vs Custom 64k's 0.138% due to Gemma's 256k multilingual vocabulary, though Custom maintains far superior fertility: 1.147 vs 2.308). At 32k, only TinyLlama_Sindhi records lower fertility on the FLORES+ split, but it carries a fatal character-deletion defect.
  2. Drastic Multilingual Fragmentation: LLaMA 3.2 fragments Sindhi at 2.896 tokens per word with 28.5% byte fallback, while BLOOM fragments at 2.627 with 31.7% byte fallback. Our 64k model improves efficiency by 60.4% over LLaMA 3.2.
  3. Round-trip length check: CustomSindhi records 0.0000% normalized-length loss across the evaluated corpora. This does not establish exact character identity.

Defect Analysis: Character Deletion in Baselines

During evaluation, automated round-trip consistency tests ($S \to \text{encode} \to \text{decode} \to S'$) uncovered critical silent data-corruption defects in prominent open-source Sindhi tokenizers:

Defect 1: TinyLlama_Sindhi Silently Deletes U+06C1 (HEH GOAL)

TinyLlama_Sindhi (a 42,681-vocab community model) exhibits a 0.4147% worst-case normalized-length decrease, shortening 24.9% of FLORES+ sentences. Because the character ہ (U+06C1) was omitted from its training vocabulary and byte fallback was disabled, the tokenizer deletes the character without warning:

  • Input: هي ڪتاب تمام سٺو آهي
  • TinyLlama Reconstructed: ي ڪتاب تمام سٺو آي (هي corrupted to ي; آهي corrupted to آي)
Defect 2: FahadQazi_BPE Silently Deletes ASCII/Latin Characters

FahadQazi_BPE (a 13,031-vocab BPE model) exhibits a 0.8461% normalized-length decrease, corrupting 16.2% of sentences. It silently discards Latin alphabet characters (A–Z, a–z), destroying URLs, brand names, code snippets, and English loanwords.

In contrast, CustomSindhi models show no character loss in our round-trip check on all four evaluation sets. Byte fallback decomposes characters without a dedicated piece into UTF-8 byte tokens. The check counts net deletions only, so it does not prove exact identity for arbitrary input.

Reproducibility Guide

All scripts, configurations, and evaluation harnesses required to reproduce our reported findings are provided in the repository:

1. Clone the repository and install development tools

bash 
git clone https://github.com/alinawazcode/sindhi-tokenizer.git
cd sindhi-tokenizer
python -m pip install -e ".[dev,training]"

This source install is for development and training. For ordinary tokenizer use, install the published package with python -m pip install sindhi-tokenizer as shown above. Training requires a prepared text corpus, which is not bundled in this repository; see the training guide and data source notes.

2. Train a model from a prepared corpus

bash 
# One sentence per line; the model files are written to models/
python training/train_tokenizer.py --corpus corpus.txt --out-dir models --vocab-sizes 64000

3. Evaluate one local SentencePiece model

bash 
# The text file should contain one sentence per line.
python evaluation/metrics.py --model models/sindhi_custom_64000.model --text data/test_sentences.txt

This command evaluates one model against one text file; it does not recreate the full benchmark matrix. For the benchmark materials and results, see the repository notebooks and benchmark results guide.

Frequently Asked Questions

SentencePiece Unigram operates via global likelihood maximization and subword pruning rather than greedy bottom-up merges. In Sindhi, where prefixes, stems, and pronominal clitic suffixes frequently concatenate, Unigram preserves true morphological roots far more reliably than BPE. Furthermore, Unigram natively supports subword regularization during downstream model training.
Our empirical Pareto analysis indicates that expanding vocabulary from 64k to 150k only yields a marginal fertility improvement of 0.022 tokens/word (1.147 to 1.125), while increasing embedding table memory by over 134%. 64k achieves the optimal equilibrium of compact model footprint and single-token word coverage (88.6%).
When byte_fallback=True is specified in SentencePiece, any character absent from the subword vocabulary is decomposed into its individual raw UTF-8 byte tokens (values from 0x00 to 0xFF). Because every Unicode character has a well-defined UTF-8 byte representation, the model never emits an unknown token symbol for otherwise representable UTF-8 input. Round-trip behavior should still be checked for each tokenizer and text-normalization path.
TinyLlama's vocabulary (built with LlamaTokenizer) omitted key Perso-Arabic characters such as U+06C1 (HEH GOAL) without defining byte fallback. Because the missing codepoints had no valid mapping or explicit fallback subword, the decoder emitted empty strings for those slices rather than an explicit <unk> symbol. This masked the defect as 0.000% UNK while shortening text in 24.9% of FLORES+ sentences. The round-trip normalized-length check exposed this shortening; it does not establish exact identity for all other inputs.
The SDK exposes SentencePiece IDs and pieces for downstream preprocessing and model workflows. For Hugging Face Transformers or vocabulary expansion, use a tokenizer configuration supported by your target architecture and validate that tokenizer IDs match the model embedding table. The SDK itself is not a transformers.PreTrainedTokenizer subclass.
